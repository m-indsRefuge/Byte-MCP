Byte-MCP V1.1 is complete as a hardened, permissioned, locally operational, read-only Model Context Protocol server for explicitly approved Windows folders.

The project is not classified as a deployed ChatGPT app. That deployment requires a supported ChatGPT account capability and a compatible remote MCP connection. Those are external deployment dependencies rather than missing Byte-MCP implementation work.

## Completed product boundary

V1.1 exposes exactly four tools:

- `list_roots`
- `list_directory`
- `search`
- `fetch`

The accepted server:

- accepts approved root aliases rather than arbitrary absolute paths;
- rejects parent traversal, symbolic links, and Windows junction traversal;
- blocks common secret-bearing names, directories, and key formats;
- bounds search scope, file size, content extraction, and response size;
- extracts supported text, PDF, DOCX, XLSX, PPTX, and ZIP metadata content;
- calculates SHA-256 for fetched files;
- records allowed, denied, and unexpected-error outcomes in a local append-only audit ledger;
- fingerprints search queries and opaque references rather than storing raw values in audit;
- treats retrieved file content as untrusted data rather than instructions;
- binds only to loopback hosts;
- supports Streamable HTTP only;
- has no write, rename, delete, execute, shell, process-control, registry, or unrestricted-path tools.

## Restricted remote-profile proof

```text
Approved root alias:  share
Local folder:          %USERPROFILE%\Byte-MCP-Share
Exposed tools:         fetch, list_directory, list_roots, search
Server binding:        127.0.0.1:8000

```

The restricted profile passed local loopback listener validation and MCP discovery. `list_roots` returned only the `share` alias, and MCP discovery returned exactly the four accepted read-only tools.

No Downloads, Documents, or Projects root was exposed by that test profile.

The restricted profile and its audit ledger were stored outside Git and are not part of the release artifact.

## Remote-integration experiment

Cloudflare `cloudflared` version `2026.7.3` was installed and used to create an account-less Quick Tunnel.

Observed evidence:

- Cloudflare connectivity pre-checks passed;
- DNS resolution passed;
- QUIC connectivity passed;
- HTTP/2 fallback connectivity passed;
- the Cloudflare API was reachable;
- the tunnel registered successfully through a Johannesburg edge location;
- Byte-MCP remained bound to `127.0.0.1`;
- no inbound firewall port or router forwarding was created.

The remote MCP smoke test through the generated `trycloudflare.com` endpoint did not complete. The MCP client reported an `ExceptionGroup` containing a TaskGroup failure. The current smoke-test client did not expose the nested exception, so the exact request-level root cause was not proven.

Cloudflare documents Quick Tunnels as development-only and states that they do not support Server-Sent Events. This makes a Quick Tunnel an unsuitable accepted deployment path for a protocol client that may use an event stream, but this closeout does not claim that SSE was conclusively the sole cause of the observed failure.

A stable named Cloudflare public hostname would require a domain routed through Cloudflare DNS. No active domain was available for this project, and purchasing or configuring a domain solely to bypass the current ChatGPT account limitation was rejected as disproportionate work.

Official Cloudflare references reviewed on 2026-08-06:

- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/
- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/

## External ChatGPT dependency

OpenAI's current documentation states:

- full MCP support is available to ChatGPT Business and Enterprise/Edu;
- Pro users can connect custom MCP servers with read/fetch permissions in developer mode;
- ChatGPT does not connect directly to localhost;
- a private-network or developer-machine MCP server requires a supported remote connection such as Secure MCP Tunnel.

The active user account is ChatGPT Plus and does not currently provide the required custom MCP registration path. A third-party tunnel can solve network reachability, but it cannot add a missing ChatGPT plan entitlement.

Official OpenAI reference reviewed on 2026-08-06:

- https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt-beta

## Freeze decision

V1.1 is frozen at the accepted read-only contract.

The following changes require a new version and a separate review:

- any write, rename, move, delete, or rollback tool;
- any shell, process, registry, application-control, or arbitrary HTTP capability;
- any non-loopback server binding;
- any authentication or public-endpoint implementation;
- any change to denied names, suffixes, link handling, or containment policy;
- any additional approved root in a remotely exposed profile;
- any integration with B87 Chess Arena or another Byte-Nolan system.

The branch `build/byte-mcp-i2-chess-capability` remains a separate future capability line and is not part of V1.1.

## Release acceptance

Byte-MCP V1.1 may be released and tagged when:

- this closeout documentation is merged into `main`;
- the documentation-only pull request passes Windows and Ubuntu CI;
- the pull request contains no credentials, local configuration, audit data, or temporary tunnel hostname;
- the final merged commit is tagged `v0.1.1`;
- the release notes identify ChatGPT deployment as an external dependency rather than a completed integration.

## Final statement

Byte-MCP V1.1 is the first completed Byte-Nolan software project: a small, deterministic, security-bounded MCP server that performs its defined local read-only role and has a documented, evidence-based boundary around what was not deployed.
